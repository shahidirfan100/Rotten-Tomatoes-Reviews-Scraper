# API Discovery — Rotten Tomatoes Reviews Scraper

First file to read when the actor starts failing. It records where reviews come from, the
fetcher that works for each endpoint, and what the 401s mean.

## Summary

Two sources, both served by Rotten Tomatoes itself:

- **Movie page** `https://www.rottentomatoes.com/m/{slug}` — plain HTML, always public.
  Provides movie metadata (`vanity`, `mediaScorecard`, `reviewsData`) and a featured
  sample of 6 critic + 6 audience reviews. Used for metadata and as the fallback.
- **Reviews page** `https://www.rottentomatoes.com/m/{slug}/reviews/{reviewType}` — the
  page HTML contains no review list. Its JavaScript calls the internal review API
  `/napi/rtcf/v1/movies/{emsId}/reviews`, which returns 20 reviews per page and supports
  "Load More" pagination. The API rejects plain HTTP clients with `401`, but succeeds
  from inside a real browser session because the Akamai sensor is generated by the
  site's own JavaScript. The actor never calls the API directly; it reads the responses
  the page itself makes.

## Fetcher per endpoint (verified 2026-11-11)

| Endpoint | Fetcher | Result |
|---|---|---|
| `/m/{slug}` | Scrapling `AsyncStealthySession`, real Chrome headful | `200`, full HTML |
| `/m/{slug}` | plain HTTP (urllib / impit) | `200`, full HTML (works from this host; not relied on) |
| `/m/{slug}/reviews/{type}` | Scrapling `AsyncStealthySession` (real Chrome → bundled Chromium → headless) | `200`; page JS fetches the review API |
| `/napi/rtcf/v1/movies/{emsId}/reviews` | page's own XHR inside the browser session | `200` JSON, 20 reviews/page, cursor pagination |
| `/napi/rtcf/v1/movies/{emsId}/reviews` | direct request (impit, urllib, page `fetch()`) | `401`, empty body |

The browser chain is tried in this order and the first one that starts is used:
real Chrome headful, bundled Chromium headful, bundled Chromium headless. A blocked page
restarts the session with a new proxy URL.

## Review types and page paths

| `reviewType` | Page path | API query |
|---|---|---|
| `all-critics` | `/reviews/all-critics` | `type=critic&topOnly=false&verified=false` |
| `top-critics` | `/reviews/top-critics` | `type=critic&topOnly=true&verified=false` |
| `all-audience` | `/reviews/all-audience` | `type=audience&topOnly=false&verified=false` |
| `verified-audience` | `/reviews/verified-audience` | `type=audience&topOnly=false&verified=true` |

`pageCount` is always 20. The next page is requested by clicking
`[data-pagemediareviewsmanager="loadMoreBtn:click"]`; the API returns
`pageInfo.hasNextPage`, `endCursor` and `startCursor`.

## Pagination behaviour

- Page 1 loads automatically. Each click adds 20 reviews; `max_pages` caps the clicks.
- The page sometimes fires the same request twice. Duplicate successful URLs are ignored
  by the actor so a page is not counted twice.
- When the last page has `hasNextPage: false` the "Load More" button is removed.

## What the 401 means

`GET /napi/rtcf/v1/movies/{emsId}/reviews` from a plain HTTP client returns `401` with
`content-length: 0`, a `set-cookie: eXr91Jra=...` (Akamai sensor seed) and an
`akamai-grn` header. Adding `Accept`, `Referer`, `Origin`, `sec-fetch-*`, US-geo cookies,
or replaying captured sensor headers does not help.

Inside a stealth browser the site's own XHR usually succeeds. It can still return `401`
for some requests, including requests the site fires itself; the site retries immediately
and often gets `200`. The actor waits for the successful response and re-clicks "Load
More" a bounded number of times when a request fails. The 401s are per-request sensor
validation plus per-IP rate limiting, not a permanent gate.

Observed on 2026-11-11: several pages load, then a burst of `401`s, then recovery after a
pause; repeated fast runs from one IP eventually hit a longer block. A rotating proxy is
the fix for that case: each session restart requests a new proxy URL through
`Actor.create_proxy_configuration()`.

| `BzqJ15zRQXtAdNgMi` | Apify Proxy enabled | review API `200`, 2 pages → 40 items (the requested cap), `SUCCEEDED` |
| `paa299RWLMjHbscwQ` | Apify Proxy `RESIDENTIAL` | review API `401` → 6 items |
| `tkoTC9UAWmgUyvWAM` | none, build 1.0.8 | `401`, single fast attempt, 6 items in 37s |

Without a proxy the cloud IP is rejected by Akamai while the movie page stays public, so
the actor degrades to the 6 featured reviews. With a proxy it collected the full paginated
list while the gate was open. This is an IP-reputation issue, not a parser or browser issue.

## Why there is no reliable client-side bypass (tested 2026-11-11)

The 401 is a decision made by Rotten Tomatoes' edge, not a missing header:

- Playwright Firefox 153 and patchright Chromium both get `401` on the review API from the
  same IP where the movie page returns `200`.
- jQuery-free readers get the same result: `r.jina.ai` (its own browser and IP) renders the
  reviews page with no review list and no critic names.
- Apify Proxy datacenter and `RESIDENTIAL` exits both get `401`; one datacenter exit
  returned 40 reviews earlier the same day, then the gate closed again.
- Rotten Tomatoes' own front end calls the same endpoint and renders an empty list, so the
  page is broken for normal visitors too while the gate is closed.
- Fandango (RT's owner) answers `403` to non-browser clients.

Published alternatives return the same public sample, not a bypass:

| Service | Full review list? | Evidence |
|---|---|---|
| `gio21/rotten-tomatoes-scraper` | No | README: "No individual review text" |
| `recordsdata/rotten-tomatoes-scraper` | No | Pricing: "Up to 12 per title, as published on the title page" |
| `fortuitous_pirate/...ratings-reviews` | No | `includeReviews` = critic snippets from the title page |
| `maximedupre/rottentomatoes`, `parseforge`, `dami_studio`, `axlymxp` | No | scores/metadata actors |
| crawlora / vee3 / parse.bot | No | already recorded above: public-page derived |
| Jina Reader (`r.jina.ai`) | No | renders the page with no review list |

The only sanctioned way to get more than the featured sample is Rotten Tomatoes' licensed
data feed, which provides scores and review snippets under a commercial agreement. There
is no public endpoint that returns the full list while the gate is closed.

## Fallback

If no review API response arrives, the actor parses the movie page:

- `<review-card-critic>` web components (slots `name`, `publication`, `timestamp`,
  `rating`, `review`, `review-link`) — 6 featured critic reviews.
- `script[data-json="reviewsData"]` → `reviews[]` — 6 featured audience reviews.
- `script[data-json="vanity"]` → `emsId`, `value` (slug), `title`, `lifecycleWindow`.
- `script[data-json="mediaScorecard"]` → Tomatometer and Popcornmeter blocks.
- `#critics-consensus` → critics consensus text.

The featured set is a Rotten Tomatoes product decision, not a parser limitation.

## Rejected candidates

| Candidate | Result |
|---|---|
| `/napi/rtcf/v1/movies/{emsId}` | `401`, empty |
| `/napi/rtcf/v2/movies/{emsId}/reviews` | `404` |
| `/napi/movie/{emsId}/reviews/user` | `404` |
| `/napi/movie/{emsId}/criticsReviews/all` | `404` |
| `/cnapi/movie/{emsId}/reviews/all` | `404` (retired) |
| `?type=user` / `?page=2` on the reviews page | ignored; the client always requests `type=critic`, page 1 |

## Notes

- `emsId` comes from `script[data-json="vanity"]` (`.emsId`) or `reviewsData.vanity.emsId`.
- Slugs can redirect (`/m/oppenheimer` → no featured cards;
  `/m/oppenheimer_2023` → cards). Prefer the canonical slug supplied by the user.
- `mediaScorecard` exposes `scorePercent`, not `score`, so the `tomatometerScore` and
  `audienceScore` fields stay absent unless RT changes the payload. This matches the
  previous Node behaviour and is intentionally not "fixed" here.
